## The `factory` command

Run it from any folder inside the project or an agent worktree. `./factory install-shim` puts a small `factory`
command on your PATH that runs the `./factory` of whichever project you're in, so each project uses the factory
version it pins. `factory help` lists everything.

| Command | What it does |
|---|---|
| `factory loop [N]` | Starts an agent loop: one fresh, unattended Claude run per task (`claude -p`). `N` caps the number of tasks. Run it again in another terminal for another agent |
| `factory loop -i [N]` | The same, but each task opens a normal session you can watch and type into. It closes by itself when the task is done. On a terminal it runs in its own tmux window (session `<repo>-<name>`, window `<role>-<name>`) and shows it here (`switch-client` when you are already in tmux); starting a name that already runs only says so and shows it. Without tmux it runs here, with a note |
| `factory coding-agent\|dev-manager\|product-owner [name\|N] loop [-i] [--once] [--dry-run]` | The three roles, started the same way and run by the same loop. `factory loop` is `factory coding-agent loop`. [Roles](roles.md#roles) |
| `factory prd [--open] [--story N] [--json]` | Progress against the PRD from GitHub: per user story its tasks and state. [Product owner](roles.md#the-product-owner-factory-prd-and-the-sign-off-and-testing-queue) |
| `factory artifacts pull\|status\|list` | The project's artifacts and designs as reviewed copies in the repo, with a manifest; `status` says which copy is older than its artifact. [Artifacts](roles.md#artifacts-and-designs-factory-artifacts) |
| `factory signoff ls\|add\|plan\|confirm\|result` | The sign-off and testing queue: what only a person can check, and test plans for the running app |
| `factory init [--dry-run]` | The project's scaffold after `install.sh`: role folders, labels, the owner queue, a starter PRD and the PRD-change PR template; adds nothing twice (see [From an idea to a first milestone](roles.md#from-an-idea-to-a-first-milestone)) |
| `factory prd --stage [--ask vision\|design\|plan]` | Where the project is on the way to a first milestone, and the owner's gates |
| `factory init-roles [--force]` | Creates the project's role folder (`.claude/factory/roles/<role>/README.md` and `reads.md`) |
| `factory agent <name\|N>` | Opens Claude in that agent's folder (created the first time), with Remote Control on, for manual work there. To run the queue, use `factory loop -i` |
| `factory next` | Shows the job the factory would hand out next. It does not claim it: the last line says so and shows the command that does, `bun --no-env-file --config=/dev/null .claude/hooks/next_task.ts --claim <agent> --pid $$`. `next_task.ts --claim <agent> --issue <n>` (issues mode) claims that one issue for the agent if it is free and its dependencies are done; a taken, blocked or missing issue is refused with `{code, message, fix}` and nothing changes. The dev manager uses it to hand a builder a named task. Inside an agent session the agent comes from the environment, so the skills' commands carry no shell variable (unattended, Claude Code asks before running one and nobody answers): plain `next_task.ts` claims as `FACTORY_AGENT` with `FACTORY_PID` when both are set, `next_task.ts --issue <n>` claims as `FACTORY_AGENT`, `--no-claim` only looks, and `factory_claims.ts done` and `release` take `FACTORY_AGENT` when `--agent` is left out; an explicit `--claim`, `--pid` or `--agent` wins. In issues mode, `next` and the loop's `--dry-run` also print on stderr `Skipped #N: <agent> still holds it and is down` with the `factory issues release N` that frees it (an agent that is down or silent, not yet swept) |
| `factory rereview plan\|prompt\|record\|reply` | Incremental re-review (#70): `plan` says whether a reviewer's next round is a delta or a full review and why; `prompt` prints its instructions (the delta, its earlier findings, the agent's reply); `record` stores a round's result; `reply` stores the agent's answer to it. `--kind` is reviewer, arch, safety or security |
| `factory reset-run [--apply]` | Before a test run (#229): without `--apply` prints a plan, one line per leftover of an earlier run in this project: this machine's stale local claims, open Agent issues of an agent that is down or never ran (never one whose agent is alive here, and not one of a down agent that runs on another machine, which may only be offline there, unless you name it with `--agent NAME`, #236), exited CI containers and offline idle runners of this project's own `factory ci` names, and a `CI_RUNS_ON` / `CI_RUNS_ON_LIGHT` variable that asks for self-hosted runners when none with those labels is online. With `--apply` it does each step and prints what it did; a second run finds nothing. Errors are `{code, message, fix}`. It touches nothing outside this project's folder, repo and containers |
| `factory review-pass reviewer\|arch` | A review agent records its pass for the current commit (#197): writes HEAD's id to `<git common dir>/factory-reviews/<branch>.ok` (`.arch.ok` for `arch`), which the PR gate reads. The folder is in the git folder, which agents can't write, and the gate lets only the `reviewer` subagent record `reviewer` and the `architecture-reviewer` record `arch` (#260). It is the only command the reviewer needs for this, so no chained shell has to be allowed. Run it only when there is no must-fix item |
| `factory manager-claims list\|next\|review\|answer\|release\|sweep\|merge\|ask` | Several dev managers at once (#99): claim a PR or a question with a lease so two managers never do the same one, and see who holds what. See [Several managers at once](dev-manager.md#several-managers-at-once) |
| `factory lessons [show\|check\|suggest\|add\|prune]` | The curated lessons file (#72): `show` prints it (the builder and the reviewers read it first), `check` keeps it under `lessonsCap`, `suggest` proposes lessons from recent must-fix comments, review findings and CI failures, `add` and `prune` change it (dev manager only) |
| `factory status [--json]` | The whole factory at a glance, across machines, read-only: agents from their agent issues (working, idle, silent, down), this machine's claims, open PRs (draft, CI, the reviewer's pass when the marker is on this machine, hold, the dev manager's must-fix or approval by the gate's rule, so an approval of an older commit or from a login not in main's `trustedReviewers` shows as stale or not at all, "a person merges this one"), the CI queue and runners, and the tasks (ready by milestone, in progress, in review, blocked; plan mode: the next task). A section GitHub can't answer says so |
| `factory cockpit` | The cockpit (#308, PRD US-10): one terminal window on tmux 3.2 or newer, also over plain ssh. It runs on its own tmux server with its own prefix, `C-a`, so a tmux you nest it in keeps `C-b`. On the left, SESSIONS (every machine's, with their state and a "needs you" badge when one waits on a question or has an owner ask on its task) and the VIEWS: Needs you, Pull requests, Tasks & PRD, CI, Agents & machines, Settings, Health & releases, Usage & lessons. Enter on a session shows its real Claude Code session on the right (through `factory follow`), and you type into it; `C-a C-a` comes back to the list. A view opens as a popup that runs the existing commands through `less -R` (`1`–`8`, or Enter); Pull requests runs `factory cockpit --prs`. `:` opens a command bar: type part of a command and Enter runs the best match. On top, `factory cockpit --status`; at the bottom of each pane, its keys. A new owner-queue ask rings the terminal bell from the list once (#310, PRD US-12), at the same look that puts it in the badge and the "Needs you" count; the first look only records the asks already open, several cockpits open at once ring once between them (markers in `cockpit-rung/` in the state folder), and the cockpit adds no desktop notice (that is `factory alerts`). `C-a d` leaves the cockpit; run it again to come back. The owner's actions (#309, PRD US-11) run from the bar through the same commands as the command line: `owner merge`, `owner label`, `owner answer`, `owner release`, `owner start`, `owner stop` and `say`. Each first asks ``Run `factory <command>`? It changes <what>. [y/N]``; only `y` (or `yes`) runs it, and any other answer runs nothing (`Not run: nothing changed.`). They act on this machine's tmux, never the cockpit's own server. In the list, `s` on a session opens the bar with `say <name>` typed in, `x` with `owner stop <name>`, and `n` with `owner start`. Other commands that change things are refused, and the ones the agents and the gate use (`review-pass`, `wait`, `run-check`, `guard`, `rereview`, `manager-claims`) are never offered. A read-only command typed in the bar runs only as offered: a flag, or a word after a command that takes none (`claims release`, `next --claim`), is refused; an action takes the rest of the line as typed (`owner label 12 factory:ready --remove`). The tmux config is written to `cockpit.tmux.conf` in this machine's state folder each time. The panes run `factory cockpit --sidebar` (the list; off a terminal, one frame sized by `COLUMNS` and `LINES`) and `--bar [<words>]` (the command bar, with the words typed in already; off a terminal, the words or else one line from stdin, and the next line on stdin answers an action's question); `factory cockpit --needs` is the Needs you view from the cache, and works by hand too: each owner ask and PR only a person merges, with its link and age, and what to do about the selected one; `j` `k` move, `r` reads the snapshot again, `q` closes; off a terminal, one frame sized by `COLUMNS` and `LINES`. The views draw with Ink (decision 0002): the release's bundle, or `cockpit/ui.tsx` in a my-skills checkout. View 6, Settings, runs `factory cockpit --settings --color`. Without tmux 3.2 or a terminal it stops with `{code, message, fix}` |
| `factory cockpit --prs [<n>]` | The cockpit's Pull requests view (#338, PRD US-13; `C-a 2`), towards its board. One row per open PR: number, title (with ` · protected` when a person merges it), the agent, CI judged by the manager's one rule, the dev manager's word on the head (`✓ approved`, `✕ must-fix`), who acts next (you, the manager, the agent or CI) and the next action. Below, the selected PR's detail: branch and agent, head commit and its age, the newest marker (and an older one when none names the head), any review claim, CI job by job, open questions, protected paths and the next action, with its link. The data is `factory prs --json`. On a terminal `j` `k` (or the arrows) move, `r` reads again from GitHub, `q` closes; `NO_COLOR` turns the colour off. Off a terminal it prints one frame sized by `COLUMNS` and `LINES` with no colour, PR `<n>` selected (else the first), within 20 s: when `factory prs --json` takes longer, the frame says so and what to run. A narrow terminal drops the reviews, by, next and who-acts columns in turn. When GitHub can't be read it says so and what to run; a number that is not an open PR, or a word that is not a number, stops with `{code, message, fix}`. `m` merges the selected PR (#309, PRD US-11) after a y/N question, through `factory owner merge <n> --head <the head shown>`: a PR whose head moved since the view read it is refused with `pr_changed` and not merged; any key then reads the list again |
| `factory cockpit --json` / `--status` | The core the cockpit's screens read (#298, PRD US-1). `--json` prints one snapshot: `sessions` (every machine's, from `factory agents ls --json`, with the role from the heartbeat row), `needsYou` (owner-queue asks nobody answered or the product owner replied to, with `state` `open` or `owner`, not those still the product owner's; and PRs only a person merges), `pulls`, `ci` (from `factory ci status --json`), `version`, `doctor` (the summary of `factory doctor`), `counts` and `missing` (each part that couldn't be read, as `{code, message, fix}`); it exits 0 offline. `--status` prints one line for tmux's status line, such as `factory: 3 sessions, 1 working · 2 PRs · CI main success · 1 need you`, from the cache in this machine's state folder, so it makes no GitHub call; when the cache is empty or older than `FACTORY_COCKPIT_CACHE_SECONDS` (default 300, since a refresh costs a few GitHub calls per open PR) it starts one refresh in the background and says how old the line is |
| `factory cockpit --ci` | The cockpit's CI view (#339, PRD US-13), drawn after its board and opened with `4` in the cockpit. From the cockpit's cache (the `ci` part of `factory cockpit --json`), so it makes no GitHub call: three cards (where jobs run, with `factory ci use local` or `github` to switch; the heavy runners wanted on this machine and where that count comes from, with how many are installed here; the offline runners left over, with `factory ci clean`), then each runner with its lane and whether it runs a job, waits for one or is offline (`●`, `○`, `✕`), then the queue and the recent runs on main and open PRs with their age, and runs queued too long. What `factory ci status --json` couldn't read is shown with its fix, and the last line says how old the snapshot is. Read-only: it names the commands (`factory ci log`, `ci logs`, `ci runners N`, `ci clean`, `ci install`, `ci use`, `turbo status`) and the owner runs them. It fits `COLUMNS` (else the terminal's width), stacks the cards under 96 columns, and prints no colour with `NO_COLOR` or `TERM=dumb`; the glyphs and words carry every state |
| `factory cockpit --usage` | The cockpit's Usage and lessons view (#341, PRD US-13), drawn after its board and opened with `8` in the cockpit. From this machine only, so it makes no GitHub call: each task of the last 7 days (the period of `factory usage`) with its agent (from its `<project>-agents/<name>` worktree, else `—`), its budget (the `Budget for this task:` line the loop put in the task's first prompt, else `budget.builder`, else `none`), a bar of what it used (fresh input + output, as `factory usage` counts it; cache reads are not counted) with the percent (`over` from 100%) and the subagent that spent most; then four figures (tasks, the median of used against budget, tasks over budget, the median tokens per task), and the lessons file with how many of `lessonsCap` it holds. Rework rounds and CI runs are on GitHub, so it names `factory report` for them. Read-only: it names the commands (`factory usage --by`, `--since`, `--task <n> --budget`, `factory report`, `factory lessons suggest`, `add`, `prune`). It fits `COLUMNS` (else the terminal's width), puts each task on two lines under 80 columns, and prints no colour with `NO_COLOR` or `TERM=dumb`; the bar's glyphs (`█` used, `░` left) and the percent carry every state |
| `factory cockpit --settings [--color]` | The cockpit's Settings view (#340, PRD US-13), opened with `6` in the cockpit (it runs `factory cockpit --settings --color`): the settings as a table (setting, value, from, what it does), the project's by section under PROJECT (via PR) and this machine's under THIS MACHINE (direct). "from" is `main` (set in `.claude/factory.json`), `your change` (staged with `factory settings set --stage`, shown as "(pending)"), `this machine` or `default`; a ◆ marks a setting whose change needs a sign-off (the owner's, or a dev manager's label). A box lists the staged changes as the one pull request `factory settings pr` opens, and the last lines name the commands that edit, since the view only reads. It is plain text unless `--color` is given and `NO_COLOR` is not set; a terminal narrower than the table gets each setting over several lines. It refuses in an agent session (`cockpit_agent_session`) |
| `factory cockpit --ink` | The cockpit on Ink (#365, decision 0002), which will replace the hand-drawn sidebar and views; for now the smallest screen: `cockpit (Ink)` and the sessions (name, state, role, machine) from the cockpit's cache, read now when there is none. A release carries the UI as one JavaScript file, `.claude/hooks/factory_cockpit_ink.js`, made by `bun build` from `software-factory/cockpit/ui.tsx` (`tools/build_release.ts`): it runs under Bun with no `node_modules` and nothing to install. In my-skills it runs the source, which needs `bun install --frozen-lockfile` in `software-factory/`. On a terminal `q` or Esc leaves; off one it draws once. Without the file it stops with `cockpit_ui_missing` and says to run `factory update`; `factory doctor` says whether the file is there and loads |
| `factory prs [--json] [--since-days N] [--fresh]` | The one list a dev manager starts a pass from, read-only and REST only: every open PR with its head and age, labels, CI judged by one rule, the newest marker per commit, any review claim and a next action (`review`, `merge`, `wait CI`, `rerun flake`, `waiting for agent`, `owner merges (protected)`, `held by <manager>`, `none`); below them the unanswered questions, owner asks and quiet agents. `prs`, `watch` and `messages ls` answer from one cache in this machine's state folder while it is fresh (`views.cacheSeconds`, default 45 s; 0 turns it off), say how old it is (`(as of 12 s ago; --fresh asks GitHub again)`, on stderr with `--json`) and, from half that age, refresh it in the background; `--fresh` asks GitHub now. A list with a part GitHub couldn't give is never kept. [Details and the `--json` schema](dev-manager.md#the-list-a-manager-starts-from-factory-prs) |
| `factory cockpit watch <item>` | Watch a sub-manager (#307, PRD US-4). When the dev manager's loop runs in its own tmux window (`factory dev-manager loop -i` on a terminal, `factory resume`), each sub-manager runs in its own window too: session `<repo>-<name>-<item>`, window `dev-manager-<name>-<item>`, showing what it does as readable lines, also kept in `.git/factory-manager/<name>.d/<item>.out`. `watch` attaches to that window read-only (`tmux attach -r`) and never sends keys. A sub-manager that has ended, has no window or never ran is an error with the fix: the log to read, or how to start one |
| `factory machine [show\|setup <names>]` | This machine's id and agent names; `setup` writes the names file and refuses a name another machine has live |
| `factory autostart [status\|install\|uninstall]` | Makes this machine bring the factory back after a reboot: the dev stack and its agents, with unfinished work saved and left in place. `status` shows what would start; `install --agents haile,tewodros` turns it on and installs the boot service (systemd user unit with linger, or a LaunchAgent). [Details](agent-loops.md#after-a-reboot-factory-autostart) |
| `factory resume [--dry-run]` | What autostart runs at boot: waits for Docker and the network, runs `commands.stackUp`, starts this machine's agents in detached tmux sessions, each in its own window `coding-agent-<name>`, through the same step as `loop -i`. Safe to run by hand: running agents are left alone |
| `factory claims` | Which agent holds which folder and task on this clone (live or stale) |
| `factory reviews` | Which extra reviews and checks the current change needs |
| `factory env [name\|N]` | The ports and database of this folder, or of that agent |
| `factory worktree <name\|N>` | Prints that agent's folder (creates it the first time): `cd "$(factory worktree taytu)"` |
| `factory follow [<agent>]`, `say`, `remote` | Watch and talk to an agent by name, on this machine, another machine or in the cloud: the list shows where each agent and sub-manager runs, its state and its Remote Control link; `follow <agent>` attaches (`--read` to watch only, `--on local` for this machine only), `say <agent> "text"` types one line, `remote add <name> <user@host>` says how to reach a machine. [Details](agent-loops.md#watch-and-talk-to-an-agent-factory-follow) |
| `factory agents ls [--json] [--local] [--fresh]` | Every agent in one table: kind, where it runs, state (working, waiting, idle, down), task, since, last seen, how to follow it. [Details](agent-loops.md#the-heartbeat-daemon) |
| `factory agents [list\|card\|sweep]` | Issues mode: who is working, idle or down. `list --json` and `card <name>` give each agent's card. `sweep` marks silent agents down and releases their issues, but never those of an agent that is alive and waiting |
| `factory heartbeat [status\|install\|uninstall\|restart\|once\|run]` | The per-machine daemon that knows what each agent here is really doing. [Details](agent-loops.md#the-heartbeat-daemon) |
| `factory messages [ls\|new]` | Questions, answers and status between agents, the dev manager and the PO. `ls [--to X] [--state S] [--ref N] [--fresh]` lists the open ones across issues and PRs (from the views' cache while it is fresh, like `factory prs`); `new --kind question --to po` prints the envelope to paste into a comment. [Details](agent-loops.md#messages-between-agents) |
| `factory alerts check\|watch [--every S]` | For the owner: one terminal bell and one desktop notice per new owner-queue ask (osascript on macOS, notify-send on Linux; nothing to install). `check` looks once and prints `needs you: <id>: <text>` per new ask, or `nothing new`; the first look only records the asks already open. `watch` looks every S seconds (default 60) in this terminal until stopped. What it has seen is kept in `alerts.json` in the state folder, so an ask alerts once, and one that came while the machine slept alerts at the next look. With no desktop session (plain ssh) or no notifier, the bell still rings and the reason is said once |
| `factory issues [cmd]` | Issues mode: `list` (default), `show N` (the issue text, then the people's comments; factory marker comments are left out; `--comments` is taken too, for the form agents know from `gh`), `peek`, `new`, `tick`, `review`, `block`, `release`, `stale`, `give-back --agent NAME` (the loop runs it when a run ends: an issue the agent holds with no pushed branch, no open pull request and not in review goes back to ready; it prints `released #N` or `kept #N`), `setup` (makes the labels, including `tests-reviewed` and `deps-reviewed`, and prints `created NAME` or `already there: NAME` for each). `review N` prints one line, such as `#7 is in review: added factory:in-review, removed factory:in-progress.` (or `#7 was already in review: nothing changed.`) |
| `factory report [--since D]` | Per task PR, from GitHub: claim to PR to merge in hours, rework rounds, CI runs and failures; medians for the merged ones; for merged tasks with a budget, used against budget and the median ratio. [Measuring it](agent-loops.md#measuring-it) |
| `factory usage` | Tokens per task (or `--by agent`, `--by model`, `--by role`: manager sessions against builder ones) from this machine's Claude Code logs; `--record "label"` appends a row to the usage log. [Measuring it](agent-loops.md#measuring-it) |
| `factory usage --task <n> --budget` | The checkpoint for a task's token budget: used, budget, left and the percent, counting fresh input (input + cache writes) + output; a warning from 80%. Exit 0 always: a budget is advice. `--task <n> --markdown` (the PR comment) adds used against budget and the top subagent. [Token budgets](agent-loops.md#token-budgets) |
| `factory settings` | The interactive menu (in a terminal): browse by section, `/` to search, `?` for the long help of a setting, change, reset, review the diff and save (write the file, or open a pull request). In a pipe it prints the list. Non-interactively: `list [--section S] [--json]`, `get`, `set`, `unset`, `help [<key>]`, `diff`, `validate`, `pr`; `--local` is the same for this machine's own settings. `set --stage` and `unset --stage` collect project changes (from the cockpit, or one by one) without writing the file; `diff --staged` lists them, `unstage [<key>]` drops one or all, and `pr` opens one pull request with all of them, built on origin's main branch from any checkout, after checking each staged value again. Machine settings are saved at once, never staged. Agents can't change settings. [Details](settings.md#factoryjson-settings) |
| `factory verify` | Runs what CI runs (`commands.ci`) for the current commit and records a pass; a ready PR needs it when `commands.ci` is set. [Details](reviews-and-gates.md#the-pr-gate) |
| `factory fix` | Formats and auto-fixes the files this branch changed (`commands.fix`); the Stop check and `factory verify` run it first, so style never costs a turn |
| `factory run-check <command>` | Runs a check or test quietly: one line if it passes; if it fails, the first errors (capped by `checkOutputLines`) and the path of the full log |
| `factory check` | Runs the style checks CI runs (`styles[].check`) |
| `factory guard` | Runs the Factory guard on the current branch against `origin/<main>` (without labels) |
| `factory bootstrap machine\|project\|all\|status\|uninstall` | Set up a sandboxed factory machine: the dedicated user, rootless Docker and the network guard. The plan is printed first; `--apply` (as root) runs the privileged steps, `--script FILE` writes them as a bash script. Ends with `factory doctor --sandbox`. [Details](sandboxed-machine.md#a-sandboxed-machine-factory-bootstrap) |
| `factory doctor` | Checks this machine and project and prints `ok`, `fix` (with the fix) or `note` per line: git, Bun (every factory command and hook runs with it; the fix says how to install it), Claude Code, GitHub access (a real `gh api user` call; `gh auth status` failing alone is only a note), Node against `.nvmrc` and the `packageManager` (when there's a `package.json`), Docker and whether it's rootless (when there's a compose file), the submodules, `.claude/factory/settings.json` (the agents' rules, passed when the factory starts an agent) and that its hook lines run the Bun hooks (`bun --no-env-file --config=/dev/null "$CLAUDE_PROJECT_DIR"/.claude/hooks/<name>.ts`, each one there), a note when an old `.claude/settings.json` still holds the factory's rules (#258), the mode an unattended run starts with and its allow list, that `origin/<mainBranch>` exists (a clone of an empty repo has no fetch setting; the fix is printed), that `mainBranch` is GitHub's default branch (a fix otherwise: the loop and the PR gate must read the same branch), on a project with a release pin the same checks `factory update` ends with, `.env.local`, sops and `SOPS_AGE_KEY_FILE` (when there's a `.sops.yaml`; it never decrypts or prints a secret), the model each session role will use (the `models` setting, else what `ANTHROPIC_MODEL` or the `model` key of the project's or your Claude Code settings resolves to, else a note that it can't tell, with the command that pins one; no call is made and nothing else is read from those files), whether an unattended agent can run `commands.test` alone and through `./factory run-check` (#249; a fix names the `permissions.allow` rules to set), whether Claude Code trusts the project folder and each agent worktree (a git worktree of a trusted main working tree counts as trusted, and the line says so; it ignores the whole allow list in a folder it does not trust; doctor only reads the flag in `~/.claude.json`, never writes it or prints the file), CI (only `gh api` reads: the `CI_RUNS_ON` and `CI_RUNS_ON_LIGHT` variables and whether a runner with that label is online, whether the newest run on the main branch is green, in-progress issues held by a down agent and Agent issues for names that are not configured, a workflow whose pnpm/Node steps or commands do not match `factory.json`, and the merge boundary on GitHub (#261): a fix when this machine's gh login is an admin of the repo or main does not require the `Factory guard` check and a review, a note when the login can't read it), every `.claude/hooks/` script a workflow calls exists and a job that runs Bun sets it up (#254), the role folders, the dev manager's and the product owner's settings profiles (each resolves, its hooks exist, and it allows every command its skill names), `trustedReviewers` (a fix when it is empty in issues mode, #260), the artifact copies, a Python `commands.test` run once to see it runs tests, the shim and `FACTORY_AGENTS`, and autostart (tmux, the boot service, linger), and the shared build cache when `turbo.api` is set (a note when it can't be reached; it never runs `turbo.secretsCommand`). Read-only; exits 1 when something needs fixing. `--sandbox` adds the checks of a bootstrapped machine |
| `factory release <agent>` | Drops an agent's local claims, for example after a crash. Prints one line, such as `Released taytu: the checkout and the task claim issue-5.`, or `Nothing to release: haile holds no checkout or task claim.` |
| `factory clean` | Removes agent worktrees no live agent uses and that have no uncommitted work, and local task branches whose task is done |
| `factory wait <pr> [minutes]` | Waits for a PR to merge (default 30 minutes), polling GitHub once a minute, without spending tokens |

[Waiting](agent-loops.md#waiting-without-tokens) |

The lines, and `--json`, come from the views' cache while it is fresh, like `factory prs` (#347: GitHub's limit is shared); `--fresh` reads GitHub now. The orchestrator reads GitHub each cycle, but a pull request's comments only when the PR changed. [The orchestrator starts from it](dev-manager.md#run-a-manager) |

| `factory manage-tick [--dry-run]` | One dev manager tick without a model when idle: runs the precheck, prints `nothing to do` and ends (no model call) or, when it lists work, starts one `claude -p "/manage-pass"` on the manager profile with the `models.manager` flags. Run it from cron, launchd or a systemd timer. `--dry-run` prints the command and starts nothing |
| `factory version` | The installed release, the one `origin/main` pins, the newest, and what changed since. [Releases](updating.md#updating-from-releases) |
| `factory releases [--all]` | The releases that exist, with dates and a one-line note |
| `factory update [version]` | A project on releases: installs the newest full release (or the one you name, a pre-release too), with `--tasks plan\|issues` on a first install to write where tasks come from into `factory.json` (without it the install prints the choice; it never runs `factory issues setup`), checks its checksum, refreshes this machine's runner services, verifies, and leaves the diff for you to commit. Safe to run twice. `--release` starts taking releases in a project that has no pin yet. Without a pin it is the submodule update below. Refused inside my-skills itself (`[factory_repo]`) and in an agent session |
| `factory rollback` | Back to the release installed before (offline, from the download cache), refreshed and verified the same way. Refused inside my-skills itself, like `update` |
| `factory migrate-to-release [version]` | A project linked to the my-skills submodule: replaces the links the release owns with its files (the submodule is never written through), removes the links to factory files the release no longer has (the old Python hooks, #264), keeps the links to other skills (the nestjs skills), names a pre-release with the exact `factory migrate-to-release <tag>` to run when there is no full release, refuses a dirty tree, undoes everything on a failure, and prints the steps for the pull request, including the commands to drop the submodule once no link needs it (it runs none of them). Safe to run twice. Nothing from the release is run |
| `factory update [--layout new]` (no pin) | A project still on the submodule: takes the newest my-skills and relinks every link to the factory's own folders, a link still made through `kit/` too (the `kit/` forwarders are gone, #176), so every `./factory <cmd>` still starts after the update. `--layout new` is still accepted and changes nothing; `--layout old` is refused with `[layout_removed]`. [Then commit it in a PR](submodule.md#updating-the-factory) |

| `factory owner merge <pr> [--head <sha>]` | What the owner does by hand, as a command the cockpit shares (US-6). Prints `Protected paths: <paths>` (from main's `protected`, or `none`; a renamed file counts under its old name too), then merges the pull request with a merge commit (the dev manager's `merge_method=merge`, so stacked branches stay mergeable) pinned to its head (`gh pr merge --match-head-commit`) when it is open, not a draft, mergeable and CI is green (`factory_ci_judge.ts`); otherwise `{code, message, fix}` (`no_such_pr`, `pr_not_open`, `pr_changed`, `protected_owner_merges`, `pr_draft`, `checks_failed`, `checks_pending`, `not_mergeable`, `gate_refused`, `merge_failed`) and nothing is merged. `--head <sha>` (7 to 40 hex characters, the head you looked at; the cockpit's `m` passes it, #309) merges only while that is still the head, else `pr_changed`. The dev manager may run it under its gate (`manager_gate.ts` checks the exact command), never for a pull request with protected paths. Refused (`owner_only`) in a coding agent's or the product owner's session |
| `factory owner label <n> <label> [--remove]` | Adds a label to an issue or pull request, or takes it off. A label the repository doesn't have is refused (`no_such_label`; `factory issues setup` makes the factory's labels), so a typo never makes a new one. The dev manager may run it under its gate |
| `factory owner answer <ask-id> <text>` | Answers an ask in the owner queue ("Dev manager: needs the owner") with a comment starting `<!-- factory-owner-answer id=<ask-id> -->`. An unknown id is `no_such_ask` with the open ones; an ask already answered posts nothing. The owner's only: the dev manager is refused |
| `factory owner release <X.Y.Z>` | Tags main's commit `vX.Y.Z` and pushes the tag, which the release workflow publishes, when `software-factory/VERSION` on main says `X.Y.Z` (else `version_mismatch`, and no tag is made). Safe to run twice: a tag already on origin at that commit is "already published"; a failed push removes the local tag it made. The owner's only |
| `factory owner start <role> [name]` | Starts a `coding-agent`, `dev-manager` or `product-owner` session (`factory loop -i`) in its own tmux window on this machine (session `<repo>-<name>`, window `<role>-<name>`), through the same step as `factory loop -i`, but without attaching: `factory follow <name>`, or Enter on it in the cockpit, shows it (#309). Without a name it takes the role's first free one. One already running is said so and not started twice. A role it doesn't know is `bad_role`. The owner's only |
| `factory owner stop <name>` | Ends that session's tmux session (`<repo>-<name>`) on this machine (#309). One that already ended, or runs on another machine, is `nothing to stop` and exits 0. Its task stays claimed for it: start it again to go on, or `factory release <name>` gives its claims back. The owner's only |

[CI](ci.md#ci-githubs-runners-or-your-own-mac) |

[Lanes](ci.md#ci-lanes) · [Linux](ci.md#ci-on-linux) |
| `factory ci runners [<n>]` | Without a number: how many heavy runners this machine runs for this project, and where that count comes from. Which wins: `FACTORY_CI_RUNNERS`, then this machine's count, then `ci.runners` in `.claude/factory.json`, then 1. `install`, `status`, `factory update` and `factory doctor --sandbox` use that count; `factory update` never scales a machine down. | `factory ci log <pr or run>` | Prints the failed job's log trimmed to the failing step (timestamps off, about 80 lines at most), for a pull request number or a workflow run id. An agent runs `bun --no-env-file --config=/dev/null .claude/hooks/factory_ci_log.ts <number>`, which the kit's `Bash(bun --no-env-file --config=/dev/null .claude/hooks/*)` allow rule covers |
| `factory ci stale` / `check` | Are the installed runner copies older than the checkout (exit 3, a line per file), and are they fit to start (readable by the container's user, not writable by others). `factory update` runs both |
