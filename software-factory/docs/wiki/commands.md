## The `factory` command

Run it from any folder inside the project or an agent worktree. `./factory install-shim` puts a small `factory`
command on your PATH that runs the `./factory` of whichever project you're in, so each project uses the factory
version it pins. `factory help` lists everything.

| Command | What it does |
|---|---|
| `factory loop [N]` | Starts an agent loop: one fresh, unattended Claude run per task (`claude -p`). `N` caps the number of tasks. Run it again in another terminal for another agent |
| `factory loop -i [N]` | The same, but each task opens a normal session you can watch and type into. It closes by itself when the task is done. On a terminal it runs in its own tmux window (session `<repo>-<name>`, window `<role>-<name>`) and shows it here (`switch-client` when you are already in tmux); starting a name that already runs only says so and shows it. Without tmux it runs here, with a note. A coding agent past this machine's `maxCodingAgents`, in a window or here, is refused with `too_many_agents` and its fix (#596) |
| `factory coding-agent\|dev-manager\|product-owner [name\|N] loop [-i] [--once] [--dry-run]` | The three roles, started the same way and run by the same loop. `factory loop` is `factory coding-agent loop`. [Roles](roles.md#roles) |
| `factory prd [--open] [--story N] [--json]` | Progress against the PRD from GitHub: per user story its tasks and state. [Product owner](roles.md#the-product-owner-factory-prd-and-the-sign-off-and-testing-queue) |
| `factory artifacts pull\|status\|list` | The project's artifacts and designs as reviewed copies in the repo, with a manifest; `status` says which copy is older than its artifact. [Artifacts](roles.md#artifacts-and-designs-factory-artifacts) |
| `factory signoff ls\|add\|plan\|confirm\|result` | The sign-off and testing queue: what only a person can check, and test plans for the running app |
| `factory init [--dry-run]` | The project's scaffold after `install.sh`: role folders, labels, the owner queue, a starter PRD and the PRD-change PR template, and on this machine the heartbeat daemon (`factory heartbeat ensure`; where it can't run, init says why and the fix and goes on); adds nothing twice (see [From an idea to a first milestone](roles.md#from-an-idea-to-a-first-milestone)) |
| `factory prd --stage [--ask vision\|design\|plan]` | Where the project is on the way to a first milestone, and the owner's gates. With the owner queue on the message board the owner's approvals are read there (`factory board queue`, #513), else from the owner-queue issue |
| `factory init-roles [--force]` | Creates the project's role folder (`.claude/factory/roles/<role>/README.md` and `reads.md`) |
| `factory agent <name\|N>` | Opens Claude in that agent's folder (created the first time), with Remote Control on, for manual work there. To run the queue, use `factory loop -i`. Past this machine's `maxCodingAgents` it is refused with `too_many_agents` before anything is made, and so is `factory agent <name> --detach` (#596) |
| `factory next` | Shows the job the factory would hand out next. It does not claim it: the last line says so and shows the command that does, `bun --no-env-file --config=/dev/null .claude/hooks/next_task.ts --claim <agent> --pid $$`. `factory next --dry-run [--claim <agent>]` (#520) shows what that agent (or you) would take and claims nothing, ending with `Dry run: nothing was claimed.`; with `--issue` it is refused with `{code, message, fix}` (`factory issues show <n>` shows that issue). `next_task.ts --claim <agent> --issue <n>` (issues mode) claims that one issue for the agent if it is free and its dependencies are done; a taken, blocked or missing issue is refused with `{code, message, fix}` and nothing changes. The dev manager uses it to hand a builder a named task. Inside an agent session the agent comes from the environment, so the skills' commands carry no shell variable (unattended, Claude Code asks before running one and nobody answers): plain `next_task.ts` claims as `FACTORY_AGENT` with `FACTORY_PID` when both are set, `next_task.ts --issue <n>` claims as `FACTORY_AGENT`, `--no-claim` only looks, and `factory_claims.ts done` and `release` take `FACTORY_AGENT` when `--agent` is left out; an explicit `--claim`, `--pid` or `--agent` wins. In issues mode, `next` and the loop's `--dry-run` also print on stderr `Skipped #N: <agent> still holds it and is down` with the `factory issues release N` that frees it (an agent that is down or silent, not yet swept). In every mode a ready task whose PRD change hasn't merged (a `PRD change: #62` line, or on the board a `waits_for` link to that change's card, #578) is passed over, with `Skipped #N: it waits for its PRD change, PR #62, to merge.` on stderr, and claiming it by number is refused with `issue-waits-for-prd` (`task-waits-for-prd` for a plan or the board); see [Roles](roles.md). With `tasks.source: board` (#500) the tasks and their claims are the message board's: a task is shown by its id (the issue number for one imported from GitHub, `b<n>` for one filed on the board), a claim is made there and its token kept in `.git/factory/board-claims.json` (mode 600), and `--issue <n>` works too; `factory issues pick`, `peek`, `show`, `tick`, `review`, `block`, `release` and `new` act on the board, and the factory's messages go there. `factory issues review` ends the claim (the task stays in review, held by nobody), so the dev manager on any machine can mark it done. A task another agent holds is freed by `factory board sweep` once its claim is stale: a claim lasts 30 minutes, and while a builder's session runs the loop sends a heartbeat on it every 10 minutes (`factory_agents.ts keep`, #513), so only a claim whose session is gone runs out. A claim made this way also sets the agent's state on the board to `working on #<n>`. `factory doctor` says when the board can't be reached. |
| `factory rereview plan\|prompt\|record\|reply` | Incremental re-review (#70): `plan` says whether a reviewer's next round is a delta or a full review and why; `prompt` prints its instructions (the delta, its earlier findings, the agent's reply); `record` stores a round's result; `reply` stores the agent's answer to it. `--kind` is reviewer, arch, safety or security |
| `factory reset-run [--apply]` | Before a test run (#229): without `--apply` prints a plan, one line per leftover of an earlier run in this project: this machine's stale local claims, open Agent issues of an agent that is down or never ran (never one whose agent is alive here, and not one of a down agent that runs on another machine, which may only be offline there, unless you name it with `--agent NAME`, #236), exited CI containers and offline idle runners of this project's own `factory ci` names, and a `CI_RUNS_ON` / `CI_RUNS_ON_LIGHT` variable that asks for self-hosted runners when none with those labels is online. With `--apply` it does each step and prints what it did; a second run finds nothing. Errors are `{code, message, fix}`. It touches nothing outside this project's folder, repo and containers |
| `factory review-pass reviewer\|arch` | A review agent records its pass for the current commit (#197): writes HEAD's id to `<git common dir>/factory-reviews/<branch>.ok` (`.arch.ok` for `arch`), which the PR gate reads. The folder is in the git folder, which agents can't write, and the gate lets only the `reviewer` subagent record `reviewer` and the `architecture-reviewer` record `arch` (#260). It is the only command the reviewer needs for this, so no chained shell has to be allowed. Run it only when there is no must-fix item |
| `factory manager-claims list\|next\|review\|answer\|release\|sweep\|merge\|ask` | Several dev managers at once (#99): claim a PR or a question with a lease so two managers never do the same one, and see who holds what. See [Several managers at once](dev-manager.md#several-managers-at-once) |
| `factory lessons [show\|check\|suggest\|add\|prune]` | The curated lessons file (#72): `show` prints it (the builder and the reviewers read it first), `check` keeps it under `lessonsCap`, `suggest` proposes lessons from recent must-fix comments, review findings and CI failures, `add` and `prune` change it (dev manager only) |
| `factory status [--json]` | The whole factory at a glance, across machines, read-only: agents from their agent issues (working, idle, silent, down), this machine's claims, open PRs (draft, CI, the reviewer's pass when the marker is on this machine, hold, the dev manager's must-fix or approval by the gate's rule, so an approval of an older commit or from a login not in main's `trustedReviewers` shows as stale or not at all, "a person merges this one"), the CI queue and runners, and the tasks (ready by milestone, in progress, in review, blocked; plan mode: the next task). Last, this machine's GitHub calls in the last hour (counted as for `factory usage --github`): the total by agent, the top 5 callers (command and endpoint, `factory_wait answer: issues/:n/comments`) and what GitHub has left of the hour's 5,000. A section GitHub can't answer says so |
| `factory ui [--port N] [--host]` | The factory's web UI (#421, #422, [decision 0005](../decisions/0005-web-ui.md)), in a browser. A Bun server on this machine serves one page and a JSON API. It follows the owner's design (#450, `docs/design/web-ui/`): plain white and flat, with only the colours of `theme.css`, light or dark as the system is set until you pick one with the switch at the bottom of the rail (kept in the browser), and no command shown on screen. On the far left the projects (this one and each checkout listed in `ui.projects`), then the selected project's sidebar: Home, Inbox (the owner queue), Board (the tasks), Epics, Pull requests (with how many are open), PRD and decisions, Sign-off and testing, Activity; Your team (the product owner, the dev manager, then each coding agent in `agents`, each with its avatar, its role in grey and a dot for its state); Run the factory (Team, CI and runners, Machines, Health, Usage and cost, Factory settings with Integrations, Releases and updates and Maintenance as its tabs); and on the right the page under its title and a line saying what it is for. Pages not built yet say what they will hold. Home (#451) starts with Needs attention (#579), anything stuck, worked out by the server from what it already reads (the board's or the snapshot's tasks and epics, the snapshot's pull requests and CI, the agents' heartbeats, the pull requests that left the open list), with no GitHub call of its own: a task in progress whose holder is down, or that nothing moved for `attention.taskQuietMinutes` (Release); a task whose pull request is no longer open but that isn't done (Close); an agent down while it holds a task, or no dev manager or product owner running while pull requests or product asks wait (Start); a session working longer than `attention.<role>.maxMinutes` (open its output, where Stop is); a coding agent idle for `attention.idleWithReadyMinutes` while a task it may take is ready (held by nobody, handed to nobody else, waiting for no open task; on the board, ready that long too), saying so when its Claude session holds a message typed but not sent (#591) (Start work: after a confirm, `/next-task` goes to its session as the chat sends it, through `factory say`, which presses Enter instead of typing the same text twice); a task in progress or in review that is spinning (#580): its tokens or its agent's working time pass `attention.spinFactor` times the median of the done tasks (only with 5 done tasks or more), or it had `attention.spinReviewRounds` review rounds with must-fixes, or its last `attention.spinFailedCi` CI runs failed (Open its output); a pull request open longer than `attention.prWaitHours` with red checks, no review, a must-fix nobody picked up or a merge only a person can do (open the PR); an epic whose tasks are all done (Close the epic); a PRD change still an open pull request while tasks are being built (open the PR); and the message board or every CI runner down. Each item says why and has one action, which goes through the same confirm as elsewhere (Close closes the issue as completed through `gh api`, or with `tasks.source: board` moves the task or epic to done on the board; it is Needs attention's only, never on a card). The list's count shows in red beside Home in the sidebar, and a card, an epic, a task's page or an agent (its row in Your team and on Home, its page) carries a small Stuck mark with the reason (`GET /api/projects/:p/attention`, also in Home's answer; the WebSocket pushes `{type: "attention", project, items}` when it changes). Then it shows what needs you (owner-queue asks nobody answered, pull requests only a person merges, blocked tasks with their reason, failed CI on the main branch, Health's failures), the team with each agent's state and task, tasks done of all by epic, and the last 10 events, each linking to its page (`GET /api/projects/:p/home`, read from the snapshot's cache, the board, the owner queue and the agents already read). Activity (#451, #583) is one feed across agents, newest first, each entry one line with who, what, when and a link (clicking it opens its task, its pull request's page or its agent's), filtered by agent, task, epic and kind (`GET .../activity?agent=&task=&epic=&kind=`). With the tasks on the message board it shows the board's events for the project: claims, releases, blocks and moves, comments, questions and answers, notes, closes and hand-offs on its tasks, an agent starting or going down (its liveness value, not each ping), and, when the pull request feed runs, a pull request opened, pushed to, its CI passed or failed, merged or closed. Beside them is what the snapshot already read: the pull requests opened (when GitHub says they were), those that left the open list since the server first looked (merged or closed: the snapshot can't tell which), a pull request's CI passing or failing and its review (approved, or must-fixes) between two reads (kept in `ui-pulls-seen.json` in the state folder), and failed CI runs; what the board's pull request feed already told isn't told again. It makes no GitHub call of its own. A new entry is pushed over the WebSocket as itself (`{type: "activity", project, items}`), from the board as it happens and from the snapshot when it is read again, and goes on top of the page at once. With the tasks on GitHub issues it shows what the snapshot knows (and the owner's open asks) and says that claims, moves, comments and agents come with the board. Health (#455) runs `factory doctor --json` on the first look and on Check again (`POST .../health/check`, one run at a time), never on a poll since a run costs GitHub calls, and keeps the result in `ui-health.json` in the state folder: each check as ok, warning or failed with its fix, grouped as this machine, the project, the board, GitHub and CI runners. Usage and cost (#455) shows the tokens and cost each task, each agent and each day used on this machine against the budget (`factory usage --json`, `--by worker`, and `budget.builder`; the problems `factory usage` reports, such as no logs found with where it looked, and its own error when it fails, #571; a task's own `Budget:` line isn't read, it costs GitHub calls), the GitHub calls of the last hour (`factory usage --github --json`), and what isn't measured yet. Its By task view adds a table, sortable by any column, of what each task took (#580, `GET /api/projects/:p/costs`, from `factory usage --json --by task` over the last 30 days): build time, agent working time, sessions, tokens, cost, CI runs (failed) and review rounds; a task's page shows the same for the task, and an epic's page its tasks' totals; it is read again at most every `FACTORY_SNAPSHOT_CACHE_SECONDS`. The WebSocket sends `{type: "health"}` when a run ends and `{type: "activity", items}` with Activity's new entries, and these pages read again then. Team (#581) lists every role in one place: the product owner, the dev manager and each coding agent (`agents` and `roles.<role>.names`), with its avatar, role, the machine it runs on (the one it runs on now, else what this machine's settings say), its state, its task and its earlier names (`formerNames`), with Start or Stop (the agent page's confirm; Start also checks this machine's limit). Add takes a free legend name or a typed one (lowercase letters, digits and dashes) and where it runs (this machine, another machine, or choose later), and stages `agents` with it (`factory settings set --stage agents [...]`). Remove and Rename ask first, with their preconditions (it isn't running, else Stop it; it holds no task, else "Release its work first" with its Release button), refused by the server with `ui_agent_running` or `ui_agent_holds_task` otherwise; Remove stages the list without it, Rename stages the new name in the old one's place and `formerNames` with the old one (two stages, the first put back when the second fails). Rename moves nothing on the board or GitHub: since the agent is stopped and holds no task there is no claim or holder to move, the old name's heartbeat row goes down and the new one's starts when it starts, and its pull requests, branches, messages and finished tasks keep the old name. What this machine runs is its own file and is never staged: a choice made before the change is merged (a new agent for this machine, or one this machine runs leaving or renamed) waits there as `teamPending` and is applied by the next read once this checkout has the change, since a name the project doesn't have would stop the loops here. Coding agents at once on this machine saves `maxCodingAgents` for this machine (`factory settings --local set`), after a confirm that says the agents already running keep running. Each change goes into the staged bar and the settings pull request as on Factory settings, and an agent's page links to Team. Factory settings (#456) has Your team (read only, with Manage the team opening Team), Project settings and This machine. Project settings lists every setting of the settings schema (`factory_settings_schema.ts`) by section, the main ones first (main branch, test and lint commands, `tasks.source`, protected paths, `tasks.staleHours`, `manager.claimMinutes`), each with its plain name, help, value and where it comes from (From main, Default, or Staged); Edit checks the value against its type, then stages it (`factory settings set --stage`, or `unset --stage` for Back to the default). The staged changes show in one bar with Drop all (`factory settings unstage`) and Propose as a pull request (`factory settings pr --ready`, after a confirm); an open settings pull request (a `settings/` branch) shows with its link. This machine says which agents run here and where that comes from (`FACTORY_AGENTS`, or this machine's file), only whether a message board is set (never its address), and saves its settings at once (`factory settings --local set`). Releases and updates shows what this project runs, what main pins and the newest release (`factory version --json`); Update asks first (on releases, a newer one, no uncommitted changes, no agent working here), then starts `factory update` and answers at once, and the page shows how it went; there is no publish. Maintenance lists the clean-ups (`factory clean`, `factory ci clean --apply`, `factory reset-run --apply`), each saying what it will and won't touch, with a preview where the command has one, and runs one after a confirm. A settings change merged and pulled into the checkout shows without starting the page again (the API reads `.claude/factory.json` again on each call). This machine also shows how far the project's checkout is behind main on GitHub, and Bring this machine up to date (#566) moves it forward after a confirm, only when that is safe: it is the project's own folder (an agent's worktree is left to its loop), on main (or detached on a commit main has, as the loop leaves the first agent's folder between tasks), clean apart from ignored files, and with no commit of its own; then `git fetch origin <main>` and `git merge --ff-only origin/<main>` (and the submodules). When it isn't safe nothing is touched and the page says why and what to do (`checkout_not_on_main`, `checkout_dirty`, `checkout_diverged`, `checkout_agent_worktree`, `checkout_fetch_failed`). Every remove, stop or merge shows its preconditions as a checklist (the button stays off until each is met), what will happen and what won't, and for a serious one asks for the name to be typed; an item's page has a "Talk about this" box that sends one line to the product owner or the dev manager on the item's thread. Every agent has an avatar (#437), shown in the channel list, the channel's header, the chat, the tasks and pull requests and the machines channel: a picture the page draws from the agent's name and role (a coding agent wears a hard hat, the dev manager a headset, the product owner a star pin), in a colour of its own, so nothing is installed. To use your own, put an image at `.claude/factory/avatars/<name>.png` (or `.jpg`, `.jpeg`, `.webp`, `.gif`, `.svg`; 256 KB at most) in the project; when it can't be shown, the agent's initials in its colour stand in. A search box (`/` or Ctrl-K) finds a channel in any project by its name, role or state. An agent's channel shows its state (working on #n, waiting, idle, down, or waiting on the GitHub limit while that is used up), its task with its title, its role, machine, how it runs and since when, and its last lines of output when it runs on this machine (its log file, else its tmux pane); Start and Stop show their preconditions first (Stop: it is running, and on this machine; Start: it isn't running yet), then run `factory owner start <role> <name>` or `factory owner stop <name>` on this machine. The machines channel shows each machine with its agents, and the CI runners, and an Add machine card (#445): a name and the agents it will run, then, after a confirm, it runs `factory machine add <name> --json --agent ...` on the hub (`POST /api/projects/:p/machines`) and shows the join code and the one command to run on the new machine (`POST .../machines/:name/remove` runs `factory machine remove`). The epics channel (#440) shows each epic: something bigger than a task, kept as an issue labelled `epic` whose stage is an `epic:<stage>` label (`investigating`, `prd`, `decision`, `planned`, `building`, `done` or `parked`; none means investigating, and a closed epic is done), whose tasks are its `- [ ] #n` lines (done when ticked or when the issue is closed), and whose optional `PRD: <path>` and `Decisions: 0003, 0004` lines link its PRD and decisions; it shows the stage, a bar of tasks done of all, and links to its tasks, and Board's list groups tasks under their epics. Epics are not tasks: `factory next` and the task list leave them out. Pull requests lists each open one with its checks, review, protected files, who opened it (the agent from its `agent:<name>` label or its branch: `task/` a builder, `po/` or a product owner's name the product owner, `manager/` or a dev manager's name the dev manager, else the product owner's PRD-change template in its body, else a person) and what comes next; one only a person merges, or one the product owner opened for you, says "waiting for you" and carries `needsYou` for Home. Clicking one opens its page (#453; address `pr:<n>`, so Back works and it can be shared): the title, the description read as a page, who opened it, its tasks (from its branch and its `Closes`/`Part of` lines), its checks with their state and a link to each log, the reviews (the dev manager's markers and GitHub's), the protected files it touches and whether only a person may merge it, and every changed file with its diff (a Markdown file can be read as a page too, so a PRD is readable). It is read from GitHub only when the page opens (`GET /api/projects/:p/pull-requests/:n`) and kept until the snapshot shows a new head or new checks, never on a poll. Its actions are the owner's (refused with `owner_only` in a factory session) and each asks first with its preconditions: Merge (open, not a draft, checks passing) runs `factory owner merge <n> --head <sha>` (a merge commit, as the factory's own merges) and then, for a merge into main, brings this machine's checkout up to date as Bring this machine up to date does, so a merged settings change (a new agent) applies at once, or says why the checkout was left as it is, refused here first for a draft (`pr_draft`, offering Mark ready) or checks that fail (`checks_failed`) or still run (`checks_pending`); Mark ready runs `gh pr ready <n>`; Comment posts your words on it; Ask for changes posts the dev manager's must-fix marker on its head, so the author reworks it, and with the message board also a verdict message to the author on its task's thread; Close closes it, after your reason as a comment. The answer comes at once and the page and the list are read again. Board (#439; its address is `view:tasks`, and `page:board` opens it too) shows the tasks as a board or a list (By epic, By agent and List tabs): the board has a column per factory label (Ready, In progress, In review, Blocked, Done, and Not ready first when a task has no ready label yet), swim lanes by epic (the epic that lists the task, in the epics' order, else its milestone, then No epic; the default when the project has epics) or by agent (then Nobody), and a card per task with its number, title, the avatar of who holds it, one status (Needs you when its pull request waits for the owner, Checks failing when that PR is red, else its state), its pull request and that PR's checks; the filter and the epic chips narrow the cards. In issues mode a card's Release, Block and Reassign ask first, saying what happens and what doesn't (Block needs a reason; Reassign picks a coding agent), then run `factory issues release <n> "<why>"`, `factory issues block <n> "<reason>"`, or `factory issues release <n> "reassigned to <agent> from the web UI"` then `factory say <agent> "/next-task issue-<n>"` on this machine; the answer comes at once, and the board is read again right after (an action while a read runs is read again when that one ends). These change the issue's labels and claim; a session already working on the task is not stopped. An agent's channel is also a chat (#423): what the agent asked, answered and handed on (its messages, from `factory messages ls --kind all --all --json`) and what you sent from the page, which is kept on this machine in `ui-chat.jsonl` in the state folder (mode 600). The box under it sends one message: to a coding agent as `factory say <name> <text>` (one line), to the dev manager or the product owner as one turn of a talk (`factory talk`), whose answer arrives in the chat when that session ends. PRD and decisions (#438) lists, a tab each, the project's PRD (the file `prd` names), its decisions (the folder `decisions` names) and the factory's wiki, each as a readable page (headings, tables, links between pages that open in the page); the search box also finds lines in them; a task or pull request title that cites a decision (`decision 0004`, `ADR 4`) or a PRD story (`US-12`) links straight to it, and what its body cites is listed under it as links (`cites decision 0004 · US-12`; `factory prs --json` and the task trackers give each one's `cites`). Only Markdown files inside those places are served; a link in a wiki page opens only another wiki page. The owner-queue channel (Inbox) shows each ask on "Dev manager: needs the owner" (read from the message board with `factory board queue --json` when the owner queue is there, #513, else, or when the board can't be reached, from the issue) as a card with its options (its list lines) as buttons and a box for your own answer; a tap asks first, then runs `factory owner answer <id> <answer>`; answered asks show your answer. The + in the rail, under the projects, adds a project (#447), on a page of its own laid out as the design's first-launch screens: clone one of your GitHub repos (`gh repo list`), make a new one (`gh repo create --private` or `--public`, with a README), or pick a git checkout already on this machine (its top folder); a folder that already holds the checkout must have nothing uncommitted, untracked files included, since the setup commits everything in it, and a folder picked on this machine must have an `origin` remote, where its setup pull request goes (`ui_add_no_remote` otherwise, #546); then Set it up: where tasks come from (issues, a plan file, or the message board when this machine has one; `ui_add_no_board` otherwise), the main branch, the commands (test, lint, type check, install and build: each is written as given, and one left empty is cleared, never left as the template's pnpm guess, #540; a command with a control character or over 200 characters is refused with `ui_add_command`, and Review warns when one is only a runner such as `bun`, since its allow rule would let an agent run almost anything), the trusted reviewer (the GitHub login signed in here, which you can change), the protected paths, and the team (dev manager, product owner and builders from the 12 legends). Review lists what Create will do; Create asks first, saying what happens and what doesn't, then runs each step on this machine and shows it as it goes: clone or create the repo, install the factory (`install.sh` when the page runs from a my-skills checkout; a file already there is kept. When it runs from a project installed from a release, that project's release client installs the same release, from the download cache or by downloading its tag, and the step fails with the `factory update --archive` fix unless the new pin names the same archive, #537), save the answers in its `.claude/factory.json` (`tasks.source`, with `messaging.transport: board` for tasks on the board or when this project names the board; `commands.*`; `trustedReviewers`; and in `permissions.allow` the rules that let an unattended agent run the test, lint, type check and build commands, alone and through `./factory run-check`, which also go into the agents' rules in `.claude/factory/settings.json` as `factory update` puts them there, the pin following; if the pin can't be written the settings file is put back as it was), and make the kit's CI workflow run those commands from the settings, with no pnpm or Node step when the project has no `package.json` (#540), `factory init` there (labels, owner queue, starter PRD, role folders), commit it all on the branch `factory/setup` and open its pull request (never on the main branch), list the project on the left (kept in `.git/factory/ui-projects.json`, beside the token, so the next start shows it too), and `factory doctor` there. A repo with only a readme passes it; what only you can set (main's ruleset on GitHub, an agents' login with admin rights, which lets the agents get round the merge gate, Claude Code's trust question) doesn't fail the step: the step is done and lists each as a to-do with its fix (#540). `factory init` and `factory doctor` run the project's own `factory` script, so a repo that already has one runs that version.
