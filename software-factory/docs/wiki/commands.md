## The `factory` command

Run it from any folder inside the project or an agent worktree. `./factory install-shim` puts a small `factory`
command on your PATH that runs the `./factory` of whichever project you're in, so each project uses the factory
version it pins. `factory help` lists everything.

| Command | What it does |
|---|---|
| `factory loop [N]` | Starts an agent loop: one fresh, unattended Claude run per task (`claude -p`). `N` caps the number of tasks. Run it again in another terminal for another agent |
| `factory loop -i [N]` | The same, but each task opens a normal session you can watch and type into. It closes by itself when the task is done. On a terminal it runs in its own tmux window (session `<repo>-<name>`, window `<role>-<name>`) and shows it here (`switch-client` when you are already in tmux); starting a name that already runs only says so and shows it. Without tmux it runs here, with a note |
| `factory coding-agent\|dev-manager\|product-owner [name\|N] loop [-i] [--once] [--dry-run]` | The three roles, started the same way and run by the same loop. `factory loop` is `factory coding-agent loop`. [Roles](roles.md#roles) |
| `factory prd [--open] [--story N] [--json]` | Progress against the PRD from GitHub: per user story its tasks and state. [Product owner](roles.md#the-product-owner-factory-prd-and-the-sign-off-and-testing-queue) |
| `factory artifacts pull\|status\|list` | The project's artifacts and designs as reviewed copies in the repo, with a manifest; `status` says which copy is older than its artifact. [Artifacts](roles.md#artifacts-and-designs-factory-artifacts) |
| `factory signoff ls\|add\|plan\|confirm\|result` | The sign-off and testing queue: what only a person can check, and test plans for the running app |
| `factory init [--dry-run]` | The project's scaffold after `install.sh`: role folders, labels, the owner queue, a starter PRD and the PRD-change PR template; adds nothing twice (see [From an idea to a first milestone](roles.md#from-an-idea-to-a-first-milestone)) |
| `factory prd --stage [--ask vision\|design\|plan]` | Where the project is on the way to a first milestone, and the owner's gates |
| `factory init-roles [--force]` | Creates the project's role folder (`.claude/factory/roles/<role>/README.md` and `reads.md`) |
| `factory agent <name\|N>` | Opens Claude in that agent's folder (created the first time), with Remote Control on, for manual work there. To run the queue, use `factory loop -i` |
| `factory next` | Shows the job the factory would hand out next. It does not claim it: the last line says so and shows the command that does, `bun --no-env-file --config=/dev/null .claude/hooks/next_task.ts --claim <agent> --pid $$`. `next_task.ts --claim <agent> --issue <n>` (issues mode) claims that one issue for the agent if it is free and its dependencies are done; a taken, blocked or missing issue is refused with `{code, message, fix}` and nothing changes. The dev manager uses it to hand a builder a named task. Inside an agent session the agent comes from the environment, so the skills' commands carry no shell variable (unattended, Claude Code asks before running one and nobody answers): plain `next_task.ts` claims as `FACTORY_AGENT` with `FACTORY_PID` when both are set, `next_task.ts --issue <n>` claims as `FACTORY_AGENT`, `--no-claim` only looks, and `factory_claims.ts done` and `release` take `FACTORY_AGENT` when `--agent` is left out; an explicit `--claim`, `--pid` or `--agent` wins. In issues mode, `next` and the loop's `--dry-run` also print on stderr `Skipped #N: <agent> still holds it and is down` with the `factory issues release N` that frees it (an agent that is down or silent, not yet swept) |
| `factory rereview plan\|prompt\|record\|reply` | Incremental re-review (#70): `plan` says whether a reviewer's next round is a delta or a full review and why; `prompt` prints its instructions (the delta, its earlier findings, the agent's reply); `record` stores a round's result; `reply` stores the agent's answer to it. `--kind` is reviewer, arch, safety or security |
| `factory reset-run [--apply]` | Before a test run (#229): without `--apply` prints a plan, one line per leftover of an earlier run in this project: this machine's stale local claims, open Agent issues of an agent that is down or never ran (never one whose agent is alive here, and not one of a down agent that runs on another machine, which may only be offline there, unless you name it with `--agent NAME`, #236), exited CI containers and offline idle runners of this project's own `factory ci` names, and a `CI_RUNS_ON` / `CI_RUNS_ON_LIGHT` variable that asks for self-hosted runners when none with those labels is online. With `--apply` it does each step and prints what it did; a second run finds nothing. Errors are `{code, message, fix}`. It touches nothing outside this project's folder, repo and containers |
| `factory review-pass reviewer\|arch` | A review agent records its pass for the current commit (#197): writes HEAD's id to `<git common dir>/factory-reviews/<branch>.ok` (`.arch.ok` for `arch`), which the PR gate reads. The folder is in the git folder, which agents can't write, and the gate lets only the `reviewer` subagent record `reviewer` and the `architecture-reviewer` record `arch` (#260). It is the only command the reviewer needs for this, so no chained shell has to be allowed. Run it only when there is no must-fix item |
| `factory manager-claims list\|next\|review\|answer\|release\|sweep\|merge\|ask` | Several dev managers at once (#99): claim a PR or a question with a lease so two managers never do the same one, and see who holds what. See [Several managers at once](dev-manager.md#several-managers-at-once) |
| `factory lessons [show\|check\|suggest\|add\|prune]` | The curated lessons file (#72): `show` prints it (the builder and the reviewers read it first), `check` keeps it under `lessonsCap`, `suggest` proposes lessons from recent must-fix comments, review findings and CI failures, `add` and `prune` change it (dev manager only) |
| `factory status [--json]` | The whole factory at a glance, across machines, read-only: agents from their agent issues (working, idle, silent, down), this machine's claims, open PRs (draft, CI, the reviewer's pass when the marker is on this machine, hold, the dev manager's must-fix or approval by the gate's rule, so an approval of an older commit or from a login not in main's `trustedReviewers` shows as stale or not at all, "a person merges this one"), the CI queue and runners, and the tasks (ready by milestone, in progress, in review, blocked; plan mode: the next task). Last, this machine's GitHub calls in the last hour (counted as for `factory usage --github`): the total by agent, the top 5 callers (command and endpoint, `factory_wait answer: issues/:n/comments`) and what GitHub has left of the hour's 5,000. A section GitHub can't answer says so |
| `factory ui [--port N] [--host]` | The factory's web UI (#421, #422, [decision 0005](../decisions/0005-web-ui.md)), in a browser. A Bun server on this machine serves one page and a JSON API. It follows the owner's design (#450, `docs/design/web-ui/`): plain white and flat, with only the colours of `theme.css`, light or dark as the system is set until you pick one with the switch at the bottom of the rail (kept in the browser), and no command shown on screen. On the far left the projects (this one and each checkout listed in `ui.projects`), then the selected project's sidebar: Home, Inbox (the owner queue), Board (the tasks), Epics, Pull requests (with how many are open), PRD and decisions, Sign-off and testing, Activity; Your team (the product owner, the dev manager, then each coding agent in `agents`, each with its avatar, its role in grey and a dot for its state); Run the factory (CI and runners, Machines, Health, Usage and cost, Factory settings with Integrations, Releases and updates and Maintenance as its tabs); and on the right the page under its title and a line saying what it is for. Pages not built yet say what they will hold. Every remove, stop or merge shows its preconditions as a checklist (the button stays off until each is met), what will happen and what won't, and for a serious one asks for the name to be typed; an item's page has a "Talk about this" box that sends one line to the product owner or the dev manager on the item's thread. Every agent has an avatar (#437), shown in the channel list, the channel's header, the chat, the tasks and pull requests and the machines channel: a picture the page draws from the agent's name and role (a coding agent wears a hard hat, the dev manager a headset, the product owner a star pin), in a colour of its own, so nothing is installed. To use your own, put an image at `.claude/factory/avatars/<name>.png` (or `.jpg`, `.jpeg`, `.webp`, `.gif`, `.svg`; 256 KB at most) in the project; when it can't be shown, the agent's initials in its colour stand in. A search box (`/` or Ctrl-K) finds a channel in any project by its name, role or state. An agent's channel shows its state (working on #n, waiting, idle, down, or waiting on the GitHub limit while that is used up), its task with its title, its role, machine, how it runs and since when, and its last lines of output when it runs on this machine (its log file, else its tmux pane); Start and Stop show their preconditions first (Stop: it is running, and on this machine; Start: it isn't running yet), then run `factory owner start <role> <name>` or `factory owner stop <name>` on this machine. The machines channel shows each machine with its agents, and the CI runners. The epics channel (#440) shows each epic: something bigger than a task, kept as an issue labelled `epic` whose stage is an `epic:<stage>` label (`investigating`, `prd`, `decision`, `planned`, `building`, `done` or `parked`; none means investigating, and a closed epic is done), whose tasks are its `- [ ] #n` lines (done when ticked or when the issue is closed), and whose optional `PRD: <path>` and `Decisions: 0003, 0004` lines link its PRD and decisions; it shows the stage, a bar of tasks done of all, and links to its tasks, and Board's list groups tasks under their epics. Epics are not tasks: `factory next` and the task list leave them out. Board (#439; its address is `view:tasks`, and `page:board` opens it too) shows the tasks as a board or a list (By epic, By agent and List tabs): the board has a column per factory label (Ready, In progress, In review, Blocked, Done, and Not ready first when a task has no ready label yet), swim lanes by epic (the epic that lists the task, in the epics' order, else its milestone, then No epic; the default when the project has epics) or by agent (then Nobody), and a card per task with its number, title, the avatar of who holds it, one status (Needs you when its pull request waits for the owner, Checks failing when that PR is red, else its state), its pull request and that PR's checks; the filter and the epic chips narrow the cards. In issues mode a card's Release, Block and Reassign ask first, saying what happens and what doesn't (Block needs a reason; Reassign picks a coding agent), then run `factory issues release <n> "<why>"`, `factory issues block <n> "<reason>"`, or `factory issues release <n> "reassigned to <agent> from the web UI"` then `factory say <agent> "/next-task issue-<n>"` on this machine, and the board is read again. These change the issue's labels and claim; a session already working on the task is not stopped. An agent's channel is also a chat (#423): what the agent asked, answered and handed on (its messages, from `factory messages ls --kind all --all --json`) and what you sent from the page, which is kept on this machine in `ui-chat.jsonl` in the state folder (mode 600). The box under it sends one message: to a coding agent as `factory say <name> <text>` (one line), to the dev manager or the product owner as one turn of the cockpit's talk (`factory cockpit --chat-send`), whose answer arrives in the chat when that session ends. PRD and decisions (#438) lists, a tab each, the project's PRD (the file `prd` names), its decisions (the folder `decisions` names) and the factory's wiki, each as a readable page (headings, tables, links between pages that open in the page); the search box also finds lines in them; a task or pull request title that cites a decision (`decision 0004`, `ADR 4`) or a PRD story (`US-12`) links straight to it, and what its body cites is listed under it as links (`cites decision 0004 · US-12`; `factory prs --json` and the task trackers give each one's `cites`). Only Markdown files inside those places are served; a link in a wiki page opens only another wiki page. The owner-queue channel shows each ask on "Dev manager: needs the owner" as a card with its options (its list lines) as buttons and a box for your own answer; a tap asks first, then runs `factory owner answer <id> <answer>`; answered asks show your answer. The owner queue is read again at most every `views.cacheSeconds` (45) while the channel has been opened. It stays live: while a page is open the server reads every project again each `ui.pollSeconds` (5) through `factory agents ls --json` and the cockpit's cache, and pushes what changed over a WebSocket. It listens on 127.0.0.1 only, at `ui.port` (4747; `--port` wins, `0` picks a free port); `--host` also listens on this machine's Tailscale address (`tailscale ip -4`), and is refused with `tailscale_missing` without Tailscale. On start it prints `open: http://127.0.0.1:<port>/?token=<token>`, the token, and `Ctrl-C stops it.`; the token is kept in `.git/factory/ui-token` (mode 600, the same at each start) and every API call and the WebSocket need it (401 `ui_token_missing` or `ui_token_wrong` otherwise). The owner's: in an agent session it is refused with `owner_only`. A release carries the page as one file, `factory_ui_app.js`, with nothing to install; a my-skills checkout builds it from `web/app.tsx` at start |
| `factory cockpit` | The cockpit (#308, PRD US-10): one terminal window on tmux 3.2 or newer, also over plain ssh. It runs on its own tmux server with its own prefix, `C-a`, so a tmux you nest it in keeps `C-b`. On the left, SESSIONS (those that run on this machine, or are down but named in its names file, then the other machines' live ones marked `on <machine>`; each with its state, `working`, `waiting`, `idle`, `down`, or `unknown` when its machine stopped reporting, `nohup` when it runs outside tmux, and a "needs you" badge when one waits on a question or has an owner ask on its task), OTHER PROJECTS (the other projects on this machine with their agents, shown and not picked, #395) and the VIEWS: Needs you, Pull requests, Tasks & PRD, CI, Agents & machines, Settings, Health & releases, Usage & lessons, Talk to the dev manager (`9`), Talk to the product owner (`0`) and Messages (`m`: `factory messages tail`, live; Ctrl-C closes it). Enter on the dev manager or the product owner opens the talk with it ([The cockpit](cockpit.md)); Enter on another session shows its real Claude Code session on the right (through `factory follow`), and you type into it; `C-a C-a` comes back to the list. A view opens as a popup (`1`–`8`, or Enter), each one `factory cockpit --<view>` drawn on Ink: `--needs`, `--prs`, `--tasks`, `--ci`, `--agents`, `--settings --color` (paged by `less -R`, whose `/` searches it), `--health` and `--usage`; in each, `j` `k` move or scroll, `/` filters its rows, `r` reads again and `q` closes. `/` in the list, or `C-a /` from any pane, opens the search across the views (`factory cockpit --search`, #392). `:` opens a command bar: type part of a command, `↑` `↓` pick among the matches (the best first), and Enter runs it; a read-only command's output is paged by `less -R`, an action asks first and shows its output, and a refused line shows its message and fix. On top, `factory cockpit --status`; at the bottom of each pane, its keys. A new owner-queue ask rings the terminal bell from the list once (#310, PRD US-12), at the same look that puts it in the badge and the "Needs you" count; the first look only records the asks already open, several cockpits open at once ring once between them (markers in `cockpit-rung/` in the state folder), and the cockpit adds no desktop notice (that is `factory alerts`). `C-a d` leaves the cockpit; run it again to come back. The owner's actions (#309, PRD US-11) run from the bar through the same commands as the command line: `owner merge`, `owner label`, `owner answer`, `owner release`, `owner start`, `owner stop` and `say`. Each first asks ``Run `factory <command>`? It changes <what>. [y/N]``; only `y` (or `yes`) runs it, and any other answer runs nothing (`Not run: nothing changed.`). They act on this machine's tmux, never the cockpit's own server. In the list, `s` on a session opens the bar with `say <name>` typed in, `x` with `owner stop <name>`, and `n` with `owner start`. Other commands that change things are refused, and the ones the agents and the gate use (`review-pass`, `wait`, `run-check`, `guard`, `rereview`, `manager-claims`) are never offered. A read-only command typed in the bar runs only as offered: a flag, or a word after a command that takes none (`claims release`, `next --claim`), is refused; an action takes the rest of the line as typed (`owner label 12 factory:ready --remove`). The tmux config is written to `cockpit.tmux.conf` in this machine's state folder each time. The panes run `factory cockpit --sidebar` (the list, on Ink when its UI is installed (#366), else drawn by hand; `r` reads it again; off a terminal, one frame sized by `COLUMNS` and `LINES`; the Ink list reads `--sidebar-data` and runs its keys with `--sidebar-open`) and `--bar [<words>]` (the command bar, with the words typed in already; off a terminal, the words or else one line from stdin, and the next line on stdin answers an action's question); `factory cockpit --needs` is the Needs you view from the cache, and works by hand too: each owner ask and PR only a person merges, with its link and age, and what to do about the selected one; `j` `k` move, `r` reads the snapshot again, `q` closes; Enter on an owner ask shows it whole with its options and answers it through `factory owner answer` after a y/N (#395, [The cockpit](cockpit.md#answering-an-owner-ask)); off a terminal, one frame sized by `COLUMNS` and `LINES`. The views draw with Ink (decision 0002): the release's bundle, or `cockpit/ui.tsx` in a my-skills checkout. View 6, Settings, runs `factory cockpit --settings --color`. Without tmux 3.2 or a terminal it stops with `{code, message, fix}` |
| `factory cockpit --prs [<n>]` | The cockpit's Pull requests view (#338, PRD US-13; `C-a 2`), towards its board. One row per open PR: number, title (with ` · protected` when a person merges it), the agent, CI judged by the manager's one rule, the dev manager's word on the head (`✓ approved`, `✕ must-fix`), who acts next (you, the manager, the agent or CI) and the next action. Below, the selected PR's detail: branch and agent, head commit and its age, the newest marker (and an older one when none names the head), any review claim, CI job by job, open questions, protected paths and the next action, with its link. The data is `factory prs --json`. On a terminal `j` `k` (or the arrows) move, `r` reads again from GitHub, `q` closes; `NO_COLOR` turns the colour off. Off a terminal it prints one frame sized by `COLUMNS` and `LINES` with no colour, PR `<n>` selected (else the first), within 20 s: when `factory prs --json` takes longer, the frame says so and what to run. A narrow terminal drops the reviews, by, next and who-acts columns in turn. When GitHub can't be read it says so and what to run; when GitHub's hourly limit is used up, it says when the limit is back instead of sending you to `gh auth login` (#383; the view reads `factory cockpit --prs-data`, which is `factory prs --json` plus that sentence); a number that is not an open PR, or a word that is not a number, stops with `{code, message, fix}`. `m` merges the selected PR (#309, PRD US-11) after a y/N question, through `factory owner merge <n> --head <the head shown>`: a PR whose head moved since the view read it is refused with `pr_changed` and not merged; any key then reads the list again |
| `factory cockpit --tasks` | The cockpit's Tasks & PRD view (#367, PRD US-10; `C-a 3`), towards its board. From the project's task tracker: the GitHub issues in issues mode, else the build plan, read within the view's time limit. On top, how many tasks are in each lane (in progress, in review, ready, blocked, not ready, done) and the PRD's path, with a line when no task is ready so the coding agents wait; then one row per task (number, title, lane, who holds it), and the selected task's detail (its lane, holder, milestone or phase, how many of its todos are done, and the command that shows it). `j` `k` (or the arrows) move, `r` reads the tasks again, `q` closes. Off a terminal it prints one frame sized by `COLUMNS` and `LINES` within 20 s; a read that takes longer, or fails, says so and what to run. Read-only: claiming, blocking and releasing stay with the agents and the dev manager |
| `factory cockpit --agents` | The cockpit's Agents & machines view (#367, PRD US-10; `C-a 5`), towards its board. From the cockpit's cache (`sessions` in `factory cockpit --json`): each machine, this one first, with how many sessions it has and how many are down, then each session's name, role, state (`●` working, `◐` waiting, `○` idle, `✕` down), what it does and where (its tmux session, or `nohup` for a loop outside tmux, with `log <path>` under it when the file its output goes to is known, #395). Then OTHER PROJECTS ON THIS MACHINE: each project whose heartbeat file is in this machine's state folder, with its agents, or `not reporting` when its heartbeat stopped. What couldn't be read is shown with its fix. Read-only: it names `factory follow`, `factory say`, `factory owner start`, `factory owner stop`, `factory agents ls` and `factory machine show` |
| `factory cockpit --search [<words>]` | The cockpit's search across its views (#392; `/` in the list, or `C-a /`), with `<words>` typed in already. A box on top matches as you type: a row matches when each typed word is in it, in any case. It searches every view at once: what needs you (owner asks, PRs only a person merges), the pull requests (number, title, branch, author), the tasks (number, title, lane, holders), the CI runs and runners, the sessions and their machines, the settings (name, value, help), the doctor's fixes and the version, and the usage by task and the lessons. The results are grouped by view and each row names its view; `↑` `↓` move, Enter opens that view in the same popup on that row (`factory cockpit --prs <n>`, or `--<view> --find <row>`, which works by hand too) and Esc closes. It reads the cockpit's cache and this machine's settings and logs once, when it opens, so typing makes no GitHub call (`factory cockpit --search-data` prints what it looks through); the tasks come from the cache too, which reads them with the rest of the snapshot. The settings are left out in an agent session. Inside a view, `/` filters its rows (or a document's lines) the same way: Enter keeps the filter, Esc clears it, and `No match for "<words>".` says when nothing matches. Off a terminal it prints one frame sized by `COLUMNS` and `LINES`, with no colour |
| `factory cockpit --chat <dev-manager\|product-owner>` | Talk to the dev manager or the product owner (#395; `9` and `0` in the cockpit, or Enter on that role in the list). Type a line and press Enter: the role answers in a fresh session that reads its skill (`manage-pass` or `product-pass`), its context and the conversation so far, and acts within its rules; `<name> is answering…` shows meanwhile. A summary of each turn is posted on the owner queue, marked `<!-- factory-cockpit-chat role=<role> -->`, so the next pass sees it; it never counts as the owner's answer to an ask. Esc closes. Each line runs `factory cockpit --chat-send <role> <text> [<history-json>]`, which prints `{answer, summary}` (`summary.posted` false when there is no owner queue); a session that fails is `chat_failed` and posts nothing, and it stops after `FACTORY_CHAT_MINUTES` (default 15, at most 19, under the pane's 20-minute wait). Another role is `cockpit_usage`; in an agent session it refuses with `cockpit_agent_session`. [The cockpit](cockpit.md#talking-to-the-dev-manager-and-the-product-owner) |
| `factory cockpit --health` | The cockpit's Health & releases view (#367, PRD US-10; `C-a 7`), towards its board. From the cockpit's cache: how many of `factory doctor`'s checks pass, are to fix or are notes, each one to fix, the doctor's last line, and the factory version installed here (from the release pin, or a linked checkout's `VERSION`). `r` reads the snapshot again, which runs the doctor again. Read-only: it names `factory doctor`, `factory releases`, `factory update` and `factory rollback` |
| `factory cockpit --json` / `--status` | The core the cockpit's screens read (#298, PRD US-1). `--json` prints one snapshot: `sessions` (every machine's, from `factory agents ls --json`, with the role from the heartbeat row and how each runs, `runs`), `projects` (the other projects on this machine, from their heartbeat files: `name`, `fresh` and `agents`, #395), `needsYou` (owner-queue asks nobody answered or the product owner replied to, with `state` `open` or `owner` and the ask's `text`, not those still the product owner's; and PRs only a person merges), `pulls`, `ci` (from `factory ci status --json`), `version`, `doctor` (the summary of `factory doctor`), `counts` and `missing` (each part that couldn't be read, as `{code, message, fix}`); it exits 0 offline. `--status` prints one line for tmux's status line, such as `factory: 3 sessions, 1 working · 2 PRs · CI main success · 1 need you`, from the cache in this machine's state folder, so it makes no GitHub call; when the cache is empty or older than `FACTORY_COCKPIT_CACHE_SECONDS` (default 300, since a refresh costs a few GitHub calls per open PR) it starts one refresh in the background and says how old the line is |
| `factory cockpit --ci` | The cockpit's CI view (#339, PRD US-13), drawn after its board and opened with `4` in the cockpit. From the cockpit's cache (the `ci` part of `factory cockpit --json`), so it makes no GitHub call. First the verdict in one line (#396): `CI is stuck: no runner online for <label>; 3 PRs are waiting`, `CI is busy: all 2 runners online are running jobs; 1 run queued`, `CI is fine: 2 runners online, nothing queued`, `CI is fine: on GitHub's runners, …` (or `CI is slow` when runs queue too long there). Then three cards (where jobs run, with `factory ci use local` or `github` to switch; the heavy runners wanted on this machine and where that count comes from, with how many are installed here; the offline runners left over, with `factory ci clean`), each machine's runners (the machine read from the runner's name, this one marked `this machine`) with their lane and whether each runs a job, waits for one or is offline (`●`, `○`, `✕`), then the queue and the recent runs on main and open PRs with their age, runs queued too long, and the pull requests waiting on CI (queued or running, with how long and the branch). What `factory ci status --json` couldn't read is shown with its fix, and the last line says how old the snapshot is and names the commands (`factory ci log`, `ci logs`, `ci runners N`, `ci clean`, `ci install`, `ci use`, `turbo status`). It fits `COLUMNS` (else the terminal's width), stacks the cards under 96 columns, and prints no colour with `NO_COLOR` or `TERM=dumb`; the glyphs and words carry every state. On a terminal `j` `k` scroll, `/` filters, `r` reads the snapshot again and `q` closes, and its keys act on this machine, each after ``Run `<command>`? It <what it does>. [y/N]`` (only `y` runs it; any other key says `Not run: nothing changed.`), then the output, and any key reads the view again: `i` installs or reinstalls the runners (`factory ci install`); `l` and `g` send jobs to the self-hosted runners or GitHub's (`factory ci use local`, `github`); `+` and `-` one heavy runner more or fewer, 1 to 16 (`factory ci runners N`, which saves the count for this machine and reinstalls); `L` turns the light lane off or on through a pull request, since `.claude/factory.json` is protected (`factory settings set --stage ci.light false`, then `factory settings pr`; never on main); `c` removes the leftovers (`factory ci clean --apply`). `Tab` picks a run (`›`), Enter shows its log with no question (`factory ci log <pr or run id>`), and `R` reruns a failed run's failed jobs (`gh run rerun <id> --failed`). | `factory nats user add <agent> --role builder\|manager\|po\|owner [--project P]` | Makes the agent's nkey (Node's ed25519): the seed goes to `<messaging.creds>/<agent>.nk` (default `~/.secrets/nats/<project>/`, mode 600 in a 700 folder) and its public key with the role's permissions into the server's config, and a running server reloads. An agent publishes only on subjects that end in its own name; only a manager publishes hand-offs; deleting or purging a stream is for the manager and the owner. `coding-agent`, `dev-manager` and `product-owner` are taken as builder, manager and po. Run it again to change the role: the key is kept. `factory doctor`, when `messaging.transport` is nats, checks the server answers at `messaging.url`, the seeds' modes, and that each key publishes as itself and is refused as another agent |
